# 멜로밍 채널 페이지 원본 이식 상태

이 문서는 일정·옷장·노래책을 **원본 코드 복사 후 연결**하는 작업의 중간 상태를 기록한다. 이 브랜치는 아직 QA에 병합하거나 배포할 수 없다.

## 원본과 복사 범위

- 프론트: `meloming-front` `f8907f37e73d0b760eac3c5af2beb48714331c83`의 691개 소스 파일. `apps/web/src/meloming/`에 원본 디렉터리 구조대로 복사했다. import 별칭 `@/`를 `@/meloming/`으로 바꿨다. 한 파일의 CSS 클래스 변수 `tokenClass`는 공개 저장소 비밀값 검사에서 오탐되어 `badgeClass`로 이름만 바꿨다. 복사 후 로기챗 범위에 맞춘 11개 파일의 변경 해시는 `docs/meloming-adaptations.tsv`에 기록했다.
- 백엔드: `meloming-back` `a91393b2362ca8462328c6553f7fbe4b6703c6e1`의 관련 모듈 456개 파일과 Prisma 스키마 원본 1개를 `references/meloming-back/`에 바이트 그대로 복사했다. 이 스냅샷 디렉터리는 실행하지 않는다. 원본 옷장 서비스와 노래책 설정 서비스는 `apps/api/src/modules/channel-content/upstream/`에 복사하고 필요한 경계만 수정해 실제 API에서 실행한다. 나머지 원본 서비스는 아직 실행 코드로 이식해야 한다.
- 최초 백엔드 기준 브랜치에는 악보 서비스가 없어서 `meloming-back` QA `fe18cde9d8a1eea60448dd9878dc6b4eda43b2de`의 악보 서비스·컨트롤러·업로드·MIME·MXL 파일 5개를 `references/meloming-back-qa/`에 원본 그대로 추가했다. `docs/meloming-qa-source-manifest.tsv`에 별도 해시를 기록했다. 실행 경로의 MIME 판별은 바이트 동일하고 MXL 추출은 ESM import와 엄격한 배열 인덱스 표기만 바꿨다.
- 공개 에셋: 원본에서 실제 참조하는 프로필 외 공통 이미지·폰트 5개를 바이트 그대로 복사했다. 원본 저장소에 없는 폰트 경로는 생성하지 않았다.
- 파일별 SHA-256과 기준 커밋은 `docs/meloming-source-manifest.tsv` 및 QA 악보 출처 매니페스트에 기록했다. `python3 tools/check_meloming_copy.py`는 허용한 적용 변경을 제외한 프론트 소스와 백엔드 스냅샷의 원본 해시를 검증한다. 실제 마운트한 28개 라우트 파일도 복사한 원본과 바이트가 같은지 확인한다.

## 연결된 프론트 범위

원본 공개 일정·옷장·노래책 라우트, 옷장 상세, 노래책의 신청곡·라이브·셋리스트·방송 기록과 해당 관리 라우트, 원본 공통 채널 레이아웃과 기본 셸을 현재 Next.js 앱의 별도 경계에 직접 장착했다. 원본 컴포넌트의 화면 구조는 다시 작성하지 않았다. 로기챗 문서 루트 안에 원본 Provider 순서를 구성한 경계 파일만 새로 작성했다.

2026-09-23 범위 확정: 일정에서는 셋리스트 카드를 숨기되 기념일·일정 관리·반복 일정·공지는 유지한다. 시간표 템플릿·이미지 생성·SNS 설정은 라우트와 관리 메뉴에서 제외했으며, 아직 QA에 적용하지 않은 마이그레이션에서도 관련 테이블을 제거했다. 옷장 기능은 전체, 노래책은 신청곡·라이브·셋리스트·방송 기록과 관리 화면까지 포함한다. 멜로밍 콘텐츠 레코드나 파일은 이전하지 않는다.

현재 `pnpm --filter @rogichat/web typecheck`와 `build`는 통과한다. 이는 소스가 번들로 만들어진다는 확인일 뿐, 페이지가 QA API와 함께 실제로 동작한다는 뜻은 아니다.

## 남은 필수 연결

- 원본 프론트는 멜로밍의 `/v1/channel`, `/v1/schedules`, `/v1/songs`, `/v1/categories`, `/v1/artists`, `/v1/favorites` 및 관리·라이브·악보·신청 API 계약을 사용한다. 현재 로기챗의 `channel-content` API는 이 계약 전체를 제공하지 않는다.
- 공개 페이지에 도달하기 전 원본 서버 레이아웃이 호출하는 채널 정보·권한·메뉴 설정은 로기챗의 실제 단일 방에 연결했다. 관리자 레이아웃의 `/v1/user/me`를 로기챗 실제 세션과 영속 숫자형 사용자 별칭에 연결했다. 셋리스트 가용성 API는 아직 연결해야 한다. 프론트 빌드 성공만으로 페이지 기능이 동작한다는 뜻은 아니다.
- 일정: 원본 URL의 일정 공개·소유자 조회, 단건 조회, 생성·수정·삭제와 반복 일정 조회·저장을 로기챗의 일정 서비스에 연결했다. 원본 일정 공지 URL과 기본 방 저장도 연결했다. 원본 캘린더 조회·검색의 일정/기념일 부분과 기념일 범위 계산 원본 유틸을 연결했다. 비공개 일정은 소유자에게만 보이는 MySQL 통합 테스트를 추가했다. 셋리스트는 일정 응답과 화면 검색에서 제외한다. 원본 캘린더의 방송/클립 소스는 아직 대응 모델이 없어서 빈 배열이다.
- 옷장: 공개·관리 CRUD의 원본 URL을 연결했다. 원본 `/upload/image` 응답 계약을 로기챗 R2 저장소와 공개 이미지 읽기 경로에 연결하고, 소유자 전용 업로드 및 공개 조회를 가짜 저장소·실제 MySQL 통합 테스트로 검증했다. QA 환경의 실제 업로드·이미지 표시 및 관리자 브라우저 흐름은 아직 확인해야 한다.
- 노래책: 원본 `/v1/songs/channel/hurogi`의 목록·단건·기본 등록·수정·삭제 URL을 기존 곡 서비스에 연결하고 숫자형 채널 ID 응답을 바로잡았다. 가수·분류의 원본 공개/관리 조회도 연결했다. 원본 `ChannelMusicbookSettingsService`와 `ChannelOverlayLayout` 스키마를 방 키·인증·트랜잭션에 맞춰 이식하고 설정 조회/저장 및 난이도→숙련도 복사 API를 연결했다. 원본 `CategoryService`의 등록·수정·삭제·순서 교환·중복 검사와 가격 정규화 로직을 복사하고 분류 변경 URL을 연결했다. 원본 `ArtistService`의 등록·수정·중복 검사·연결 곡 삭제 로직을 복사하고 가수 변경 URL을 연결했다. 원본 `SongAddRequestService`의 신청·중복 방지·목록·승인·거절·취소와 `SongHelperService`의 분류 생성 코드를 복사해 관리자 노래 등록 신청 API를 연결했다. 원본 `SessionService`의 셋리스트 공개 목록·상세·가용성·관리 목록·가시성 변경 메서드를 방 키·트랜잭션에 맞춰 옮겨 URL을 연결했다. `ChannelSongRequestSettingsService`와 effective 설정 병합 함수를 원본에서 복사하고 설정 조회·저장 API를 연결했다. 라이브 세션 시작·활성 조회·설정 변경·종료·복제·공개 상태·기록 목록·상세의 원본 메서드를 옮겨 실제 DB에 연결했다. 신청곡 대기열 조회·등록·수동 추가·상태/순서 변경·현재곡·다음곡·스킵·삭제·취소·통계·곡별 이력 경로를 추가하고 재생 완료 곡이 셋리스트에 나타나는 MySQL 테스트를 통과했다. 원본 `SongRequestService`와 `SongRequestQueueService`의 관련 메서드를 선택해 방 키·사용자 별칭·트랜잭션에 맞춰 옮겼으며, 아직 완전한 기능 동등성은 검증되지 않았다. 원본 즐겨찾기 모델의 채널·사용자 FK를 로기챗 UUID로 옮기고 채널/곡 즐겨찾기 토글·상태·목록·통계·사용자·기념일·정렬 API와 즐겨찾기한 곡 목록을 연결했다. 곡 수동·엑셀 등록, CSV 다운로드와 다운로드 이력 스키마, 일괄 수정·삭제, 삭제 영향 미리보기를 실제 MySQL에서 검증했다. QA 악보 원본의 파일 형식 검증·MXL 추출과 슬롯 최대 10개·MusicXML 단일 슬롯·교체·개별/전체 삭제·재정렬을 R2 저장소에 연결하고 MySQL/가짜 저장소로 검증했다. 원본의 Clip 관계는 로기챗에 없어 셋리스트 곡 응답의 `clip`은 항상 `null`, 삭제 영향은 0이다. SOOP 플랫폼 채널 ID와 실시간 채팅·후원·오버레이 이벤트, 익명 웹 신청, 원본의 가격·랜덤 추출·쿨다운 세부 규칙은 아직 연결하거나 대조해야 한다. 로기챗에는 멜로밍의 포인트·범용 알림·앨범 아트 검색 기반 DB가 없어 원본 서비스의 해당 후속 호출도 아직 연결하지 않았다. 실제 QA 파일 업로드 확인은 아직 필요하다.
- 원본 `SongSuggestService`의 Fuse 검색·토큰화·정렬, `SongAutocompleteService`의 인기곡·제목·가수 정렬과 중복 제거, `SongQueryService`의 무작위 선택 로직을 원본 파일 복사 후 단일 방 UUID DB 경계에 맞춰 연결했다. 로기챗에는 원본의 채널별 캐시 무효화·스케줄러가 없어 자동완성 조회는 캐시 없이 원본 SQL을 실행한다. 실제 MySQL에서 추천·자동완성·무작위 조회를 검증했다.
- 원본 `SongMrVideoService`의 멀티파트 시작·파트 URL·완료·중단·삭제 계약과 최대 5GB/64MB 파트를 로기챗 R2 저장소에 연결했다. 완료 시 곡 DB 반영과 이전 객체 정리, 영상의 공개 범위 요청을 구현했다. 가짜 저장소와 MySQL로 권한·키의 곡 범위·DB 반영·삭제를 검증했다. 실제 QA R2 브라우저 직접 업로드와 CORS/범위 재생은 아직 검증해야 한다.
- 원본 프론트의 `/song-live` Socket.IO 경로를 로기챗 API의 `/socket.io`에 연결하고, 방송 시작·종료·설정 변경·신청곡 변경 이벤트를 DB 커밋 뒤 발행하도록 했다. 원본 소켓 훅은 로기챗 QA/운영 API 주소만 사용하도록 전송 경계를 조정했다. 소켓 접속·입장·이벤트 수신의 로컬 테스트는 통과했지만 실제 QA 다중 인스턴스 전달과 브라우저 연결은 아직 검증하지 않았다. 원본의 채팅·후원·가사 오버레이 이벤트는 아직 이식되지 않았다.
- 비로그인 웹 신청은 원본 설정의 `allowAnonymous`와 `requestMode`를 확인하고 브라우저의 실제 IP를 서버 키로 HMAC 처리한 신청자 ID를 사용한다. 익명 닉네임, 분당 10건 제한, 클라이언트가 보낸 신원·후원 정보 무시를 실제 MySQL에서 검증했다. 원본 프론트 API 전송 경계는 익명 신청에 한해 로그인 CSRF 조회를 건너뛰도록 조정했다. QA 브라우저 흐름과 여러 API 인스턴스에서의 동시 신청 제한은 아직 확인해야 한다.
- 현재 로기챗 Prisma 스키마에는 원본 `Song`의 영상·MR 필드, `SongVideoPreference`, 다중 슬롯 `SongSheetMusic`, 노래 등록 신청용 `SongAddRequest`를 추가하는 마이그레이션을 준비했다. `SongAddRequest`는 원본 필드를 유지하고 정수형 사용자·채널 FK만 실제 로기챗 계정·방 UUID로 바꿔 신청 API에 연결했다. 라이브 세션·신청곡·세션 설정·채널 신청곡 설정의 원본 모델과 enum도 복사해, 방·계정 UUID 외래키로 바꾼 마이그레이션을 추가했다. 이 모델에 연결된 API는 아직 없다. 원본의 SyncRoom, 클립 추출, 후원 관계는 로기챗에 대응 서비스가 없어 스키마에서 제외했다. 정수 `Channel`은 기본 방에 매핑했고 `User`는 영속 숫자형 별칭 테이블로 대응했다. 나머지 원본 관계 모델에서 이 매핑을 사용해야 한다.
- 옷장 원본 경로 `/v1/channel/:identifier/wardrobe`를 로기챗의 기존 옷장 서비스에 연결했다. 원본 프론트 API 클라이언트는 배포 환경에 따른 로기챗 API 목적지와 로기챗 세션의 CSRF 증명을 사용하도록 전송 경계를 조정했다. 원본 백엔드 서비스·컨트롤러의 나머지 범위를 실행 경로에 장착하고 로기챗 인증·업로드·외부 연동 경계에 연결해야 한다.
- 원본 채널 레이아웃의 `GET /v1/channel/hurogi`, `/permission`, `/feature-settings`를 로기챗의 실제 기본 방과 세션에 연결했다. 채널 ID `1`은 단일 채널의 공개 호환 별칭이며 매 조회마다 실제 기본 방으로 해석한다. 곡·가수·분류 수는 실제 방의 DB 레코드로 계산한다. 아직 원본의 사용자 정보, 일정·노래책 API 전체가 연결되지 않아 이 단계만으로 페이지 기능이 완성되지는 않는다.
- 원본 `ChannelProfile` 필드를 기본 방 FK로 이식하고 `/v1/channel/1/profile` 공개 조회·소유자 저장을 연결했다. 기념일 계산 함수는 원본을 복사했으며 Rogichat의 엄격한 TypeScript 배열 인덱스 규칙 때문에 `events[0]!` 표기 한 곳만 조정했다. 데이터는 이식하지 않으므로 새 채널의 기념일은 비어 있으며, 원본 프로필 편집 모달을 직접 복사해 일정 설정에서 날짜를 입력하도록 연결했다.
- 멜로밍의 실제 콘텐츠 데이터나 업로드 파일은 어느 단계에서도 이전하지 않는다. 사용자는 **코드와 스키마만** 옮기도록 지정했다.
