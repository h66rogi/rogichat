# M03 authentication boundary

2026-09-20. Implemented and fixture-tested; **real SOOP login is not released**.

## Runtime contract

- `/v1/auth/soop/start` accepts `intent=login|link`. Login requires the exact accepted
  `termsVersion=2026-09-20`; link requires the current session, exact Origin, CSRF and a session
  created within 15 minutes. There is no public test-login or arbitrary provider/user ID API.
- Backend creates a 10-minute transaction with UUID, state/browser SHA-256 digests and an
  AES-256-GCM encrypted S256 verifier. Each state has an independent HttpOnly browser cookie,
  so two first-visit tabs cannot overwrite each other's binding. Only its cookie is cleared
  on callback. Requests carrying 10 pending cookies are rejected; this is a normal-browser
  budget, not a global server bound against clients omitting cookies. Cookie input is bounded.
- Broker requests and code exchange use confidential Basic authentication, fixed registered
  callback/client/environment/transaction bindings, HTTPS, no redirects, five-second deadline
  and an 8 KiB response limit. Provider credentials and broker address stay server-side.
- Callback claims once before external exchange, then revalidates current session/account and
  transaction before committing identity/session. Provider subject is exact binary, unique,
  never inferred from nickname/avatar. Conflicting linked accounts never merge automatically.
- Session token is random, stored as a digest, seven-day expiry, audience-bound and checked
  against current account state on every request. CSRF token is session/key-bound. Hosted
  cookies are `__Host-`, Secure, HttpOnly, SameSite=Lax and Path=/ with no Domain attribute.
- Session DTO exposes only authenticated state, SOOP link status and CSRF token. Logout
  revokes the current session. Error bodies, logs and redirects exclude request/token material.
- Credentialed CORS admits one exact environment origin. Mutations require exact Origin and
  CSRF. Hosted IP limits trust exactly one Caddy hop; Caddy overwrites X-Forwarded-For and the
  deployer verifies API port/network isolation. Local/test ingress trusts no forwarded headers.
  MySQL-backed start/callback rates work across API replicas without local counter divergence.

## Configuration and release gates

`AUTH_SECRET_FILE` is mandatory in hosted API processes. It contains a 32-byte lowercase hex
`key` and optionally `broker: {baseUrl, clientId, clientSecret}`. Do not commit or log it. Without
broker configuration authentication returns 503; readiness does not falsely imply login readiness.
Worker does not read this authentication file. The same key/config must be shared by API replicas;
key replacement requires an explicit session/cookie invalidation plan.

The separately authorized authentication repository now has a dedicated broker implementation.
Its historical QA runtime is retired; QA source publication is **not** a running broker deployment.
The provider's permanent canonical subject contract and registered client/callback still need
verification. The broker deliberately returns `SUBJECT_CONTRACT_UNVERIFIED` before collecting a
provider token. Neither a synthetic fixture subject nor a display/image-path fallback may enable it.
User selected the existing production broker origin for both Rogichat QA and production. Client,
callback and audience bindings remain separate; the address is server configuration, not public
source or client configuration. Production promotion remains a separate reviewed decision.
Native mobile callback/session handoff
also remains its explicit release gate; these endpoints currently implement the web cookie contract.

## Evidence

Independent review identified shared-proxy-IP throttling and first-visit two-tab cookie races;
both are fixed with regressions. Disposable MySQL tests cover minimal HTTP DTO/CORS/CSRF/logout,
state/browser/audience binding, concurrent callback, expiry/suspension, fresh-session linking,
logout races, unique-identity concurrency, provider failure/denial, two tabs and proxy spoofing.
No production mock route or provider secret is present in fixture code.

Migration `m03_auth_terms` was generated by `migrate dev` on a fresh loopback MySQL and retained
without manual SQL edits. QA application uses the separate migrator procedure, never startup DDL.
